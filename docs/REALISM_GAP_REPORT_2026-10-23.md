# SKATER SEOUL — 목표 그래픽·게임플레이 격차 보고서

작성일: 2026-10-23  
대상: 사용자가 공유한 Skate City / skate. 스타일 목표, 현재 Unity Visual Slice, 최신 CLI 캡처와 QA 로그  
판정: **목표 미달. 현재 빌드는 기술 데모이며 상용 스케이트 게임의 시각·동작 품질에 도달하지 않았다.** 아래 점수는 이 프로젝트와 사용자가 제시한 목표 사이의 내부 평가이며 업계 표준이나 제3자 인증 점수가 아니다.

## 핵심 판정

가장 큰 간극은 재질의 숫자나 모델의 부품 개수가 아니라 화면에서 보이는 **형태와 동작의 설득력**이다. 실제 씬에는 3D 라이더, 데크, 4개 휠, 한강 배경, 콘크리트 텍스처, 트릭 상태와 HUD가 있지만, 이들이 한 프레임 안에서 하나의 고품질 스케이트 장면처럼 읽히지 않는다.

최근 보드 캡처 [3/4 보드](visual_overhaul/captures/r74-board-ratio/board/04_board_3q.png)와 사용자가 지적한 화면을 기준으로 보면 데크 노즈·테일 끝이 뭉툭하고, 외곽선이 직사각형에 가깝다. 갑판의 concave/kick 형상은 카메라 거리에서 읽히지 않고, 트럭은 블록처럼 보이며, 휠은 넓고 납작한 베이지 원통처럼 보인다. 밑면 그래픽 존재 여부나 검은 그립 단색 여부만 확인한 이전 판정은 보드 완성도를 평가하지 못했다. **단색 그립은 결함으로 보지 않는다.** R74의 보드 전체 시각 승인은 철회한다. 보드 구조와 라이딩 거리의 실루엣이 재검토되기 전에는 통과로 기록하지 않는다.

## 증거와 신뢰 범위

- 최신 보드 구조 증거: [R74 보드 3/4 캡처](visual_overhaul/captures/r74-board-ratio/board/04_board_3q.png), [밑면 캡처](visual_overhaul/captures/r74-board-ratio/board/05_board_underside.png). 밑면 인쇄는 존재하지만, 윗면·옆면·트럭·바퀴의 품질이나 라이딩 화면의 완성도를 증명하지 않는다.
- 최신 플레이 캡처: [R74 런타임 주행 프레임](visual_overhaul/captures/r74-board-ratio/01_runtime_ride.png) 및 사용자가 제공한 보드 프레임. 이전 캡처 자동화에는 이름과 게임 상태가 어긋난 이미지가 있어 화면 내 상태를 이미지 기준으로 판독해야 한다.
- 최신 Editor Play Mode 캡처 프로브 QA: [R75 결과](visual_overhaul/captures/r75-landing-compression/iteration-3/capture.log) 34 PASS / 1 FAIL. Unity Test Runner 모음은 아니다. **무릎 굴곡은 +17°/+17°로 프로젝트 assertion의 20–35° 범위를 못 채웠다.** 골반 drop 0.108m, 발 고정 최대 오차 0.006m, 260ms 복귀 오차 0.012m, 60fps 20프레임 착지 클립은 각각 제한된 수치 게이트다.
- 소스 대조에서 추가로 확인: wheel spin에 사용되는 `SceneBuilder` 반경은 0.039m지만 FBX 생성 휠 반경은 0.027m다. 따라서 로그의 47.93m `wheel arc`는 회전각에 설정 반경을 곱한 값이어서 설정상 이동과 일치할 뿐, 렌더 메시의 실제 롤률은 검증하지 못한다. 메시 반경으로 환산한 동일 회전의 표면 이동은 약 33.18m다. 또한 PRD는 반경 0.035–0.055m를 요구해 소스 메시/런타임 값과 세 기준이 충돌한다. 치수를 먼저 확정해야 한다. 상세 재분류는 [QA 보고서](VISUAL_OVERHAUL_QA.md)를 참조한다.
- 시각 에셋 정적 검사 [validation.log](visual_overhaul/captures/r75-landing-compression/iteration-3/validation.log)는 PASS다. 이 검사는 파일·머티리얼·계층 조건 일부를 검사하며 사람 눈의 품질 승인이 아니다.
- 환경 검증은 R73 콘크리트 PBR의 디자인 리뷰 통과 기록이 있다. 그 판정은 해당 텍스처/UV와 gameplay-distance readability에 한정한다.
- 보드 P1은 R72에서 실패 기록이 있고, R74는 텍스처의 sun 비율을 조정한 후보일 뿐 전체 보드 형상 게이트가 아니다. 이번 사용자 피드백 이후 보드 전체의 시각 게이트는 **FAIL / 재작업 필요**로 기록한다.
- 캡처·스크립트·PRD에 쌓인 이전 `PASS`들은 각 테스트의 범위에 한정된다. 이 보고서의 품질 판정은 사용자가 최근 제시한 실행 프레임을 반영한다.

## 원인 분석

### 1. 데크 윤곽 수식이 끝부분을 네모로 만든다

`UnityProject/Tools/generate_skateboard.py`에서 반폭이 `0.78 + 0.22 * sqrt(1 - nx²)`에 따라 줄어든다. 끝(`nx=±1`)에서도 최대 너비의 78%가 남기 때문에 nose/tail이 둥근 팝시클 형태로 좁아지지 않고 넓고 평평한 끝이 된다. 길이 방향은 36분할, 폭 방향은 12분할뿐이며 얇은 상/하면과 단순 side wall로 곡률을 표현한다. 이것이 주요한 “각지고 뾰족/네모” 인상의 구조적 원인이다.

### 2. 부품 수는 실제 부품 실루엣을 대신하지 못한다

트럭은 작은 베이스 플레이트, 여러 원통, 사각형 행어로 구성된다. 실제 행어의 가늘어지는 cast 형상과 킹핀/부싱의 관계가 읽히지 않는다. 휠은 베벨된 원통과 평평한 허브 재질 구분에 의존하며 타이어 폭·둥근 립·양쪽 bearing recess가 충분하지 않다. 또한 스크립트 휠 메시는 반경 27mm인데 `SceneBuilder`는 접지 계산에 39mm를 사용한다. 현재 물리 접지 프록시와 렌더 메시의 접점이 12mm 차이 나므로, 시각 개선 전에 통일해야 한다.

### 3. 렌더 대상 거리에 맞춘 아트 검사가 부족했다

밑면 그래픽 검사에 집중한 반면, 보드가 대부분의 라이딩 시간 동안 보이는 윗면·측면 실루엣을 실제 게임 카메라 거리에서 평가하지 않았다. 그립 색을 바꾸는 것이 문제가 아니며, 데크 노즈/테일·concave·휠·트럭의 명암과 비율을 라이딩 프레임에서 알아볼 수 있어야 한다.

### 4. 사람 눈의 스케이트 포즈 판정 대신 수치 assertion을 앞세웠다

골반 하강량과 발 위치가 통과해도 포즈가 실제 스케이팅처럼 보인다는 뜻은 아니다. 현재 리그/모션의 기본 실루엣과 스케이트보드 특유의 비대칭 발 위치, 푸시 다리의 접지/회복, 어깨·골반 counter-rotation, 트릭별 pop/flick/catch 타이밍이 일련의 연속 동작으로 설득되는지 리뷰받지 못했다. 사용자 피드백이 시각 게이트의 우선 기준이다.

## 목표에 도달하기 위해 남은 작업

### 우선순위 0 — 실패한 핵심 실루엣 교정

1. 보드 치수/축/피벗/접점의 단일 기준표를 작성하고, 렌더 휠 반경과 런타임 접지 반경을 실제 모델 bounds로 일치시킨다.
2. 데크를 둥근 nose/tail과 점진적 이중 킥이 있는 popsicle profile로 재작성한다. 길이/폭/concave 방향 분할을 늘리고, top과 underside UV는 각각 평면 매핑/출력 그래픽 영역을 명확하게 분리한다.
3. 트럭을 baseplate·kingpin·bushings·가늘어진 hanger·axle·너트로 실루엣 중심 재구성하고, 휠을 둥근 urethane profile 및 recessed bearing으로 수정한다. 부품을 무조건 늘리기보다 옆/3⁄4에서 읽히는 형태를 먼저 맞춘다.
4. 보드 단독 top/side/3⁄4/underside 네 시점과 라이딩 거리 캡처를 같은 빌드에서 생성한다. 모든 시점에서 둥근 덱 끝·정상 비율의 휠/트럭·목재 레이어·밑면 그래픽을 확인한다.

### 우선순위 1 — 히어로 스케이터

1. 현재 Quaternius 기반 메시의 얼굴, 손, 발, 의상 실루엣과 표면 결함을 실제 렌더 거리에서 감사한다.
2. 사용자 목표인 동양인 남성 힙합 스케이터의 성인 비율, 후드집업(후드·지퍼·밑단), 데님(무릎/밑단 주름), 스케이트 슈즈(낮은 실루엣·보강 토캡·평평한 벌크솔)를 가진 한 명의 캐릭터를 완성한다.
3. 신발 크기와 둥근 형태를 줄이고 앞코·발등·밑창 층을 구별한다. 보드 위 발 pose와 신발 길이/폭은 모델의 실측 비례에 맞춘다.
4. CC0/상업 허용 자산의 라이선스를 확인하고, Blender에서 메시/의상을 수정한 후 리그 웨이트를 검증한다. 자동 생성한 단순 프리미티브를 최종 인간 형태로 취급하지 않는다.

### 우선순위 2 — 스케이트 모션을 동작 단위로 재구축

푸시오프를 지지발, 지면 접촉, 뒤로 미는 발, toe-off, 보드 위 회복의 연속 동작으로 만들고, Ollie/Kickflip/Tre Flip은 crouch → pop → flick/yaw → air tuck → catch → impact → 압축·복구의 연속 클립으로 검증한다. 실제 스케이터 레퍼런스의 촬영 시점과 라이선스를 기록한다. 한 장의 포즈와 C# IK 수치만으로 승인하지 않는다. 각 동작을 같은 카메라로 60fps CLI 녹화하고, 발-보드 접촉과 몸-보드 타이밍을 프레임 단위로 확인한다.

### 우선순위 3 — 씬 통합과 게임 전체 품질

- 라이더와 보드가 화면 높이에서 충분히 큰 구도, 배경 파노라마와 3D 전경 사이의 깊이, 실제 그림자/반사광을 함께 조정한다.
- 플라자 바닥의 반복 무늬는 지나친 스케일/대비가 없는지 확인하고, ledge·레일·벤치·가로수 등 근거리 소품의 실루엣과 접촉 면을 완성한다.
- HUD의 상태·버튼·제스처·safe area를 화면 비율별로 검증하고, UI가 라이더·보드를 가리는지 기록한다.
- 동일 씬·동일 상태·동일 해상도의 전후 캡처를 유지한다. 캡처 파일명에 practice/battle, 트릭, 타임코드를 명시해 자동화 라벨 오류를 제거한다.
- 지원 기기를 특정한 뒤 iOS 빌드에서 프레임 시간, GPU/메모리, 발열, 터치 지연, 다양한 화면비를 확인한다.

## 재승인 기준

- **보드:** 사용자가 직접 제공한 목표 레퍼런스에 비추어 실제 스케이트보드 실루엣으로 즉시 읽혀야 한다. 라이딩 거리에서도 rounded nose/tail, kick/concave의 하이라이트, 데크 적층, 트럭과 4개 휠이 뭉치지 않고 보여야 한다. 단색 그립은 허용된다.
- **라이더:** 사용자가 지정한 동양인 힙합 스케이터/후드집업/데님 인상이 분명해야 하며, 발·신발 비율과 옷 실루엣이 자연스러워야 한다.
- **동작:** 정지 포즈만이 아니라 현재 Unity 빌드의 60fps 연속 영상에서 push, Ollie, Kickflip, Tre Flip의 보드-몸 협응이 이해되어야 한다. 수치 체크와 시각 리뷰 모두 필요하다.
- **환경/UI:** 실제 플레이 시점에서 한강풍 스케이트 공간이 깊이감 있게 보이고, UI/조작이 동작을 가리지 않아야 한다.
- **승인:** 개별 자산/QA 게이트와 전체 사용자 목표 승인을 별개로 남긴다. 코드 또는 정적 에셋 검증의 PASS는 사용자 시각 검토를 대체하지 않는다.

## 결론

프로젝트는 Unity 플레이어블 슬라이스, 기본 물리/트릭 루프, 한강 배경, 일부 재질과 검사 자동화를 갖췄다. 현재 가장 중요한 문제인 보드 외형, 사용자 목표에 맞는 라이더, 스케이트답게 읽히는 연속 모션은 여전히 해결되지 않았다. 특히 보드 메시는 nose/tail 실루엣과 부품 프로파일부터 다시 만들어야 한다. R74를 보드 통과로 취급하지 않는다. **현 상태의 적절한 표기는 “기술적으로 돌아가는 초기 플레이어블, 시각 품질 목표와 큰 격차”다.**

이 보고서는 저장된 Unity 캡처·코드·로그와 사용자의 화면 평가에 근거한다. 새 Unity 실행, iOS 기기 측정, 외부 전문가의 새 검토는 이번 보고서 작성에서 실행하지 않았다.
