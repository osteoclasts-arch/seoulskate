# 다음 작업을 빠르고 만족스럽게 끝내기 위한 실행 보고서

작성일: 2026-10-23  
목적: 지난 6시간 작업에서 반복된 방향 착오와 허위 통과를 줄이고, 사용자가 원하는 품질을 초기에 확인하며 구현한다.

## 핵심 원칙

다음 작업은 코드량이나 체크 통과 개수가 아니라 **실제 게임 화면에서 사용자가 차이를 즉시 알아보는가**로 진행한다. 결과가 별로면 수치상 통과해도 실패다. 사용자가 준 목표 이미지와 현재 화면을 직접 비교하고, 사용자가 문제라고 말한 부분은 즉시 최우선 결함으로 올린다.

6시간은 Skate 4 전체 품질을 새로 만드는 시간이 아니다. 하지만 범위를 보드 하나, 캐릭터 하나, 짧은 트릭 동작 하나로 제한하고 적절한 소스 에셋을 골라 연결하면, 현재보다 명확히 좋아진 **검토 가능한 히어로 장면**을 만들 수 있다. 처음부터 모든 캐릭터·배경·UI·트릭을 동시에 고치지 않는다.

## 지난 작업에서 시간이 새어 나간 이유

1. **잘못된 성공 기준:** 머티리얼 매핑, 4개 휠 존재, 골반 이동량, 발 IK 오차처럼 확인하기 쉬운 항목을 만족도를 대신하는 기준으로 썼다. 이 검사는 형태가 그럴듯한지, 동작이 스케이트처럼 보이는지 답하지 못한다.
2. **검토 순서가 뒤집힘:** 게임 카메라의 보드 실루엣과 사용자 취향을 먼저 승인받지 않고, 밑면 그래픽·수치·자동화부터 반복했다. R74 artwork 수정은 보드 외형 전체를 통과시킬 근거가 아니었다.
3. **부적절한 제작 수단:** 간단한 Blender 수식과 원시형 조합은 정확한 크기의 프로토타입에는 쓸 수 있지만, 사람의 발·옷과 스케이트보드의 자연스러운 형태를 빠르게 완성하는 수단으로는 부족했다. 근본적으로 높은 수준의 모델이 필요할 때는 기존 저폴리 모델을 계속 덧대지 말고 라이선스가 확인된 더 적합한 모델이나 제작 가능한 베이스를 먼저 찾아야 한다.
4. **지나치게 많은 축을 건드림:** 보드, 캐릭터, 환경, 트릭, HUD를 넓게 벌리고 각 영역의 작은 작업을 했지만, 어느 한 장면도 목표 수준까지 밀어붙이지 못했다.
5. **캡처의 신뢰 문제:** 실제 모드·카메라·타이밍과 파일 이름이 맞지 않는 캡처가 섞였다. 서로 다른 구도의 전후 이미지를 비교하면 개선 여부를 쉽게 오판한다.
6. **검토 결과의 과잉 해석:** 한 리뷰어가 특정 이미지/재질 항목을 통과시킨 일을 전체 보드나 전체 게임의 승인으로 확대했다. 리뷰어의 판정 범위를 그대로 유지하지 않았다.

이 문제는 사용자의 요청이 모호해서 생긴 게 아니다. 요청과 불만을 작업 게이트에 반영하지 않은 실행 측의 문제다.

## 첫 30분의 의사결정 규칙

- 기준 캡처는 **실제 게임 카메라 거리**를 사용한다. 자산 검사 카메라는 보조 자료이며 라이딩 화면을 대체하지 않는다.
- 사용자의 목표를 항목으로 고정한다. 이번 프로젝트 기준은 보드의 실제 팝시클 실루엣과 부품 비율, 동양인 힙합 스케이터의 후드집업·데님·자연스러운 스케이트화, 스케이트 전용 자세, 서울풍 공간 깊이, 플레이를 가리지 않는 HUD다.
- 단색 그립처럼 사용자가 허용한 요소는 결함으로 만들지 않는다. 색/장식 선호를 추측하지 말고 이미 받은 지시를 따른다.
- 이 작업에서 고칠 상위 1개를 고른다. 나머지는 명시적으로 보류한다. 현재 상태에서는 보드 외형 또는 캐릭터·모션 중 사용자가 선택한 핵심 불만 하나부터 끝낸다.
- 구현 시작 전에 “이 캡처가 이렇게 변하면 좋아졌다고 볼 수 있다”를 한 문장과 이미지 표시로 남긴다.

## 아트 제작 선택 기준

**보드:** 프로시저럴 제작은 규격화된 부품과 반복 생성에 사용한다. 덱 끝이 네모나지 않는 외곽선을 먼저 만들고, 실제 보드의 nose/tail 곡률, double-kick, concave, 얇은 적층, trucks의 hanger/kingpin/bushings, round-lip wheels가 읽히는지 검사한다. 렌더 휠 반경과 접지 계산 반경은 실제 메시 bounds에서 하나의 기준으로 맞춘다. 밑면 그림이 존재하는지만으로 통과시키지 않는다.

**캐릭터:** 사람 모양의 저폴리 베이스에 작은 장식을 계속 추가하는 방식은 중단 조건을 둔다. 30–45분 안에 head/body/shoe silhouette이 목표와 분명히 멀면, 라이선스가 검증된 더 좋은 rigged source asset을 조사하거나 리그/메시 교체 프로토타입으로 전환한다. 하이엔드 사실감을 짧은 시간에 직접 조각해야 한다고 전제하지 않는다. 신발은 발 길이/폭·앞코·밑창 층을 먼저 바로잡는다.

**애니메이션:** C# IK 숫자는 발 접촉과 관절 보정의 진단 자료다. 스케이트 자세의 승인 자료는 실제 카메라의 연속 영상이다. Push는 지지발·바닥에 닿는 미는 발·toe-off·보드 위 회복이 보여야 한다. Ollie/Flip은 crouch·pop·flick 또는 yaw·보드와 발 분리·catch·landing의 순서가 연결되어야 한다. 수치 통과와 시각 판정을 각각 기록한다.

## 리뷰와 도구 사용 규칙

1. Aside를 통한 웹 조사에서는 프로젝트 목표와 제약을 전달하고, 1차 출처 우선, 직접 링크, 라이선스, 확인된 사실과 제작 가정을 구분해 요청한다. 검색 결과를 길게 모으는 대신 구현 선택에 필요한 질문만 조사한다.
2. 기존 ChatGPT.com 디자인 리뷰 대화에는 정지 이미지/자산 캡처만 보낸다. 질문은 “패스입니까?”가 아니라 “실루엣·비율·재질 중 가장 치명적인 결함 1–3개와 다음 수정”으로 묻는다.
3. 기존 게임플레이 리뷰 대화에는 현재 빌드의 연속 캡처/60fps 영상만 보내고, 단계별 발-보드 연결과 무게중심 변화를 판정해 달라고 한다.
4. 리뷰 결과는 지적한 캡처와 범위를 함께 보관한다. 디자인 부분 PASS는 애니메이션/전체 게임 PASS가 아니다.
5. 화면 캡처 프로그램을 쓰지 않는다. 사용자가 정한 조건에 따라 Unity CLI 캡처와 파일 로그를 쓴다. 캡처 전 게임 모드를 명시적으로 설정하고, 결과 화면을 열어 라벨·HUD·타임코드를 직접 확인한다.
6. 파일명에는 빌드/반복 번호, 모드, 트릭/포즈, 프레임이나 초를 포함한다. 전후 비교는 카메라·해상도·노출·게임 상태를 맞춘다.

## 품질 게이트: 하나라도 실패하면 해당 자산을 통과시키지 않는다

- **G1 사용자 목표:** 현재 결과를 목표 이미지와 나란히 놓았을 때, 사용자가 반복해 불만을 제기한 형태가 실제로 개선되었나?
- **G2 게임 거리:** 기본 플레이 카메라에서 핵심 실루엣과 접점이 읽히나?
- **G3 실제 형태:** 보드라면 nose/tail·truck·wheel이, 사람이라면 관절·옷·신발이 원시 도형처럼 보이지 않나?
- **G4 통합:** 캡처가 현재 빌드/모드의 것인지 확인했나? 메시가 움직임·접촉·게임 UI를 깨지 않았나?
- **G5 검토:** 해당 리뷰어가 해당 범위를 명시적으로 승인했나? 아직 답이 없거나 전체 범위를 보지 않았다면 `미검토`로 남긴다.
- **G6 보고:** 수치 QA와 시각 리뷰를 분리해 기록했나? 각 PASS에 무엇이 통과했고 무엇이 제외됐는지 썼나?

`PASS`는 G1–G6 중 해당 게이트에서 요구하는 조건을 사람 검토와 증거로 만족했을 때만 쓴다. 자동 컴파일/정적 검사 결과에는 **기술 검사 PASS**라고만 쓴다. 사용자의 명시적 시각 불만이 새 증거를 제공하면 기존 리뷰 PASS를 다시 열고 재검토한다.
